ADR-008: Cross-Service Query Patterns

Author: Mohammad Shakhtour Open/In-Progress

Author: Mohammad Shakhtour

Status: Open/In-Progress

Summary

Decision pending on how to handle cross-service queries in microservices architecture. Current implementation returns empty strings for related data from other services. Multiple options are being evaluated.

Context

In a microservices architecture, each service owns its own database. This creates a challenge when we need to display data that spans multiple services.

The Problem:

In WorkOrderReadRepository.GetActiveWithTechnicianAndAssetAsync, we need to display work orders with technician names and asset names. In the original repo, this would be a SQL join across schema. However, in this microservices repo:

  • Work orders are stored in the WorkOrders service database
  • Technician data is stored in the Technicians service database
  • Asset data is stored in the Assets service database

Current State:

The current implementation returns empty strings for TechnicianName and AssetName:

SELECT 
    w.Id,
    w.Title,
    '' AS TechnicianName,  
    '' AS AssetName,
    w.Status
FROM workorders.WorkOrders w
WHERE w.Status <> @Completed

We need to decide on an approach to populate this cross-service data while maintaining service autonomy and architectural boundaries.

Decision Drivers

  • Service Autonomy - Each service should own its data and not depend on other services' databases
  • Complexity - Implementation and maintenance complexity
  • Latency - Query performance and response times
  • Scalability - Ability to scale independently
  • Implementation Effort - Time and resources required to implement
  • Operational Overhead - Infrastructure and maintenance requirements

Considered Options

Option 1: Cross-Database Joins (Avoid! Bad Practice)

Description:

Direct SQL joins across databases on the same SQL Server instance using three-part naming (Database.Schema.Table).

Implementation:

SELECT 
    w.Id,
    w.Title,
    t.Name AS TechnicianName,
    a.Name AS AssetName,
    w.Status
FROM workorders.WorkOrders w
LEFT JOIN technicians.Technicians t ON w.TechnicianId = t.Id
LEFT JOIN assets.Assets a ON w.AssetId = a.Id
WHERE w.Status <> @Completed

Pros:

  • Simple to implement - just SQL joins
  • Better consistency - read replica sync faster than CDC streaming
  • No additional infrastructure required
  • Low latency - single query

Cons:

  • Bad practice - Violates service autonomy and database-per-service principle
  • Deployment coupling - All databases must be on same server
  • Schema changes break queries - Changes in one service affect others
  • Violates microservices principles - Creates distributed monolith risk
  • Not scalable - Cannot scale databases independently

Why Not:

Cross-database joins fundamentally violate the microservices principle of service autonomy. While they might work as a temporary solution, they create tight coupling that defeats the purpose of microservices architecture.

Note: This would only be considered as a temporary workaround, not a long-term solution.

Option 2: CDC (Change Data Capture) with Materialized Views

Description:

Use Change Data Capture (CDC) to stream database changes to a read-optimized store that acts as materialized views (e.g., Elasticsearch, dedicated read database). Services query the denormalized read model instead of their own databases.

Key Concepts:

  • CDC (Change Data Capture): The mechanism for capturing database changes in real-time from transaction logs
  • Materialized Views: Pre-computed, stored query results that provide efficient access to aggregated/joined data
  • Relationship: CDC is the streaming mechanism that populates materialized views (the storage pattern)

Implementation:

  • Debezium captures changes from SQL Server databases (CDC mechanism)
  • Streams changes to Kafka
  • Elasticsearch consumers build denormalized read models (materialized views)
  • Services query Elasticsearch for cross-service data

Industry Practice:

This pattern is widely used in production systems. Netflix uses DBLog (their CDC framework) combined with materialized views for cross-service queries in their microservices architecture. The combination of CDC + Materialized Views is a common CQRS pattern recommended by AWS and other cloud providers.

Pros:

  • Service autonomy maintained - No direct database dependencies
  • Optimized read models - Denormalized data optimized for queries (materialized views)
  • Scalability - Can scale read models independently
  • Eventual consistency - Acceptable for read scenarios
  • Separation of concerns - Write databases for transactions, read models (materialized views) for queries
  • Real-time updates - CDC provides near real-time synchronization

Cons:

  • Infrastructure complexity - Requires Debezium, Kafka, Elasticsearch
  • Operational overhead - Additional services to maintain and monitor
  • Eventual consistency - Data may be slightly stale
  • Initial snapshot complexity - Need to handle full data dumps for initial population

Demo Repository:

A working demo of CDC with Debezium streaming from SQL Server to Elasticsearch is available at: https://github.com/mohd2sh/cqrs-beyond-database

Option 2.5: Database-Native Materialized Views

Description:

Use database-native materialized views (e.g., PostgreSQL, SQL Server) that are populated via CDC, scheduled refreshes, or database replication. Services query materialized views in a shared read database or read replicas.

Implementation Approaches:

  • CDC Populated: Use CDC (Debezium) to stream changes to a read database, then create materialized views on that database
  • Scheduled Refresh: Materialized views refreshed on a schedule (e.g., hourly, daily)
  • Incremental Refresh: Database supports incremental view maintenance (e.g., PostgreSQL, Materialize)
  • Replication-Based: Use database replication to sync data, then create materialized views on replicas

Example (PostgreSQL):

CREATE MATERIALIZED VIEW work_orders_with_details AS
SELECT 
    w.Id,
    w.Title,
    t.Name AS TechnicianName,
    a.Name AS AssetName,
    w.Status
FROM workorders.WorkOrders w
LEFT JOIN technicians.Technicians t ON w.TechnicianId = t.Id
LEFT JOIN assets.Assets a ON w.AssetId = a.Id
WHERE w.Status <> 'Completed';

-- Refresh on schedule or on-demand
REFRESH MATERIALIZED VIEW work_orders_with_details;

Industry Practice:

AWS recommends using materialized views with CQRS for microservices decomposition. Some databases like Materialize provide incremental view maintenance that automatically keeps materialized views up-to-date as source data changes.

Pros:

  • Database-native - No additional infrastructure beyond database
  • Familiar SQL interface - Standard SQL queries, no learning curve
  • Incremental refresh - Some databases support automatic incremental updates
  • Lower infrastructure cost - No need for separate search/indexing infrastructure
  • ACID properties - When using same database, benefits from transaction guarantees

Cons:

  • Database vendor lock-in - Tied to specific database features
  • Coupling risk - May require shared read database or same database instance
  • Refresh overhead - Full refreshes can be expensive for large datasets
  • Less flexible - Not as flexible as dedicated read stores (Elasticsearch, etc.)
  • Scalability limits - Limited by database scaling capabilities

When to Use:

  • When services can share a read database or read replicas
  • When using database replication for data synchronization
  • When you want to minimize infrastructure complexity
  • When incremental view maintenance is available (e.g., PostgreSQL, Materialize)

Option 3: Data API

Description:

Create a dedicated API service that aggregates and manage data from multiple services. The API makes calls to each service and composes the results.

Pros:

  • Service boundaries maintained - Each service owns its data
  • Single endpoint - Clients get all data from one API call
  • Flexibility - Can add caching, transformation, or business logic
  • Service autonomy - No database coupling

Cons:

  • Network overhead - Multiple HTTP calls
  • Latency - Sequential calls increase response time
  • Additional service - Another service to develop and maintain
  • Error handling complexity - Partial failures need handling
  • Caching complexity - Need to cache and invalidate properly

Option 4: Read Models / Denormalized Data (Event-Populated Materialized Views)

Description:

Each service maintains read models (essentially materialized views) of related data from other services, updated via domain events. This is an alternative to CDC-based materialized views, where events are the synchronization mechanism instead of database transaction logs.

Key Concept:

Read Models are materialized views populated via domain events rather than CDC. Both approaches create denormalized, pre-computed query results, but differ in the synchronization mechanism:

  • CDC-based Materialized Views (Option 2): Populated from database transaction logs
  • Event-based Materialized Views (Option 4): Populated from domain events published by services

Implementation:

  • Services publish domain events when data changes (e.g., TechnicianUpdatedEvent, AssetCreatedEvent)
  • Consuming services subscribe to relevant events
  • Event handlers update local read model tables (materialized views)
  • Queries join against local read models

Pros:

  • Service autonomy - No direct database access
  • Fast queries - Local joins, no network calls
  • Event-driven - Aligns with event-driven architecture
  • Scalability - Each service scales independently
  • Domain-aligned - Events represent business domain changes, not just database changes

Cons:

  • Storage overhead - Duplicated data across services
  • Custom Code - Need to manage the event handling
  • Event handling - Need to handle all event types
  • Data synchronization - Complex to keep in sync
  • Storage growth - Read models grow over time
  • Event ordering - Need to handle out-of-order events
  • Missing events - Need to handle missed events and replay scenarios

Industry Practices and References

Netflix

Netflix uses DBLog, a generic Change Data Capture (CDC) framework, combined with materialized views for cross-service queries in their microservices architecture. DBLog captures committed database changes in real-time and propagates them to downstream consumers, enabling loosely coupled microservices while maintaining data synchronization.

Key Points:

  • CDC framework (DBLog) captures changes from transaction logs
  • Materialized views store denormalized read models
  • Enables querying across microservices without direct database dependencies
  • Handles both real-time changes and on-demand full dumps

Reference: DBLog: A Generic Change-Data-Capture Framework - Netflix TechBlog

AWS

AWS recommends using CQRS (Command Query Responsibility Segregation) with materialized views for decomposing monoliths into microservices. The pattern separates read and write operations, using materialized views as read-only replicas optimized for specific query requirements.

Key Points:

  • CQRS pattern with materialized views for microservices
  • Read models receive queries against materialized views
  • Events trigger updates to read database, keeping materialized views eventually consistent
  • Can use DynamoDB Streams + Lambda to populate read models in Aurora

Reference: Decompose monoliths into microservices by using CQRS and event sourcing - AWS

Common Pattern: CDC + Materialized Views

The combination of CDC and Materialized Views is a widely adopted pattern in production microservices architectures:

  • CDC provides the mechanism for capturing and streaming database changes
  • Materialized Views provide the storage pattern for optimized read models
  • Together, they enable real-time data synchronization while maintaining service autonomy

This pattern is particularly effective for:

  • Cross-service queries that require data from multiple bounded contexts
  • High-performance read scenarios that benefit from denormalized data
  • Systems requiring eventual consistency with near real-time updates

References:

  • CDC in Production: An Operating Guide

Decision Outcome

Status: Open/In-Progress

Still on the TODO. The current implementation returns empty strings for cross-service data fields.

Considerations:

  • Cross-database joins are bad practice and would only be a temporary workaround if implemented
  • CDC with Materialized Views (Option 2) is a strong candidate given the existing demo repository and aligns with industry practices (Netflix, AWS)
  • Database-native Materialized Views (Option 2.5) offer a simpler alternative when infrastructure complexity is a concern
  • Event-based Read Models (Option 4) align well with event-driven architecture already in place but require more custom code
  • Data API provides a clean separation but adds latency
  • Industry leaders (Netflix, AWS) favor CDC + Materialized Views pattern for production microservices
